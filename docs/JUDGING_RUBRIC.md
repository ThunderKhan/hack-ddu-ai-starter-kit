# Track A — suggested local judging rubric (100 points)

This rubric applies to organizer-defined **local awards**, unless the official Hacktoberfest/MLH judging instructions require something different. **Official prize categories and eligibility are controlled by their current rules.**

| Category | Points | What judges should observe |
| --- | ---: | --- |
| Working functionality | 30 | The project runs, has a coherent user path and handles common errors |
| Meaningful AI use | 25 | AI is integral; the team can identify the model/library and explain inputs/outputs |
| Original improvement | 20 | A genuine addition beyond copying or rerunning the starter |
| Testing and reliability | 15 | Fair evaluation, basic tests, reproducibility, honest limitations |
| Explanation and demonstration | 10 | Clear short demo, README, fair discussion of risks |
| **Total** | **100** | |

## Score consistently

- Give observable points for **evidence**, not polish, confidence or team size.
- An unchanged starter notebook does not demonstrate original improvement.
- A basic but understandable prototype can outrank a flashy but unexplainable demo.
- Test results should reflect held-out data and avoid leakage. Failure analysis is valuable.
- Do not incentivize collecting private data or using unnecessary expensive services.
- Record team/project link and one sentence explaining each significant score.

## Independent review

Where possible, use at least 3 reviewers for a small event. Around 20 teams need 4–5 table judges circulating **during** the sprint; a 15-minute Show & Tell alone cannot cover everyone.

The attached [CSV scorecard](../templates/judging_scorecard.csv) provides fields for scores and notes. When judges disagree, compare specific evidence and log the final decision before announcing awards.
