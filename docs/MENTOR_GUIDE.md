# Organizer and mentor playbook — Track A

## Before check-in

- Open both Colab notebooks from a signed-out browser, then test running them in a Google account with CPU runtime.
- On a local machine: create virtual environment, install dependencies, run both examples and tests.
- Keep local copies and screenshots as a fallback if internet or Google services fail.
- Confirm projector, power strips, Wi-Fi and attendees' GitHub setup.
- Have a mentor computer with working Python + packages and an accessible local test dataset.
- Print a QR code to the Track A README and official event registration/project-submission location.
- Verify current official MLH challenge eligibility and organizer access before claiming any prize is guaranteed.

## Session mapping

- **11:35–12:15:** define open-source AI, models, learning vs. inference, why data/source licenses matter.
- **12:15–12:45:** live-run one notebook, show train/test split, held-out accuracy, and a visible failure. Explain Track A choices.
- **12:45–13:25:** during Git/GitHub 101, create a new GitHub repo and practice pushing a notebook; clarify separate Track A/Track B workflows.
- **13:35–13:50:** form teams and get everyone past first execution.
- **13:50–14:50:** mentors unblock teams; encourage one focused extension and meaningful measurements.
- **14:50–15:10:** collect accessible project links and begin preliminary demo review.
- **15:10–15:35:** assist official submissions; table judging and shortlist.
- **15:35–15:50:** 2–3 finalist stage demos and prizes.
- **15:50–16:00:** closing, references and group photo.

## Triage order

1. Cannot start Colab? Offer local Python on mentor machine.
2. Pip installation fails? Avoid lengthy dependency debugging; pair with a working team.
3. Notebook ran unchanged? Encourage an improvement, not a cosmetic title change.
4. Low evaluation score? Invite error analysis. Do not hide results or fabricate success.
5. Submission blocked? Note team and GitHub URL and coordinate official platform access with authorized organizer.

## Judging and privacy

- Teams should not collect personal student information, private chats, faces or real support messages.
- Validate GitHub project URLs without secrets; do not request participants' passwords or tokens.
- Do not state that a scikit-learn toy project automatically qualifies for a specific official award.
- Use the [local rubric](JUDGING_RUBRIC.md) and record the award decisions.
- Announce the winner only after organizer-required submission and judging steps are complete.

## Offline fallback

If connectivity fails, participants may work from downloaded notebooks and installed local dependencies, or work in pairs on a mentor laptop. Collect code offline and finish official submission when connectivity returns if the rules and timing allow; do not promise submission acceptance after deadline.
